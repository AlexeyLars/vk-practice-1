## 2. Поднятые сервисы — и почему именно они

Перечисли, что реально поднял (проверь через `docker ps`), и обоснуй выбор каждой технологии.

| Сервис | Роль в стеке | Почему именно он (а не альтернатива) |
|---|---|---|
| Silo (вместо MinIO) | S3-совместимое объектное хранилище файлов таблиц | Ввиду ситуации текущей с minio, заместо него используем Silo (форк MinIO с той же апишкой S3), хоть сервис в контейнере называется minio. Можно хранить данные локально и читать их из Trino и Spark через один S3 API. |
| PostgreSQL 16.10 | БД, где Lakekeeper хранит метаданные каталога | Поддерживается Lakekeeper и обеспечивает транзакционное хранение метаданных. |
| Lakekeeper 0.10.0 | Каталог метаданных таблиц | Один открытый REST-каталог для Trino и Spark, без отдельного Hive Metastore. |
| Trino 481 | SQL-движок (получает метаданные в Lakekeeper и RW данные в Silo) | Есть коннекторы TPC-H и Iceberg: можно сгенерировать данные, выполнить ELT и сравнить результат с исходным запросом. |
| Apache Spark 3.5.7 | Дополнительный движок в Docker для чтения Bronze | Проверяет, что те же Iceberg-таблицы доступны другому движку без копирования данных. |


> Если поднимал что-то ещё (или вместо чего-то) — допиши строку. В «Почему именно он» пиши не «так было в гайде», а что даёт этот выбор: открытый исходный код, S3-совместимость, коннекторы, скорость, дешевизна и т.д.

## 3. Разбор запроса — какие данные нужны

Какие таблицы и колонки TPC-H реально нужны твоему запросу.

| Таблица TPC-H | Нужные колонки | Что запрос с ними делает (фильтр / джойн / агрегат / вывод) |
|---|---|---|
| customer | custkey, name, acctbal, nationkey, address, phone, comment| custkey и nationkey джойны, остальные поля группировка и вывод |
| orders | orderkey, custkey, orderdate | Джойны клиента с заказами и позиций с заказом, фильтр по orderdate |
| lineitem | orderkey, linenumber, extendedprice, discount, returnflag | Джойн по orderkey, фильтр returnflag = 'R', сумма extendedprice * (1 − discount). linenumber оставим, чтобы делать чек по уникальности |
| nation | nationkey, name | Джойн по nationkey и вывод названия страны |

## 4. Медальон — решения по каждому слою

Как заполнять:
- **Строк** — `SELECT count(*) FROM таблица`;
- **Вес, МБ** — размер файлов таблицы в MinIO (консоль → бакет → объекты) или `SHOW STATS`;
- **Формат** — `PARQUET` / `ORC`;
- **Сжатие** — `NONE` / `SNAPPY` / `GZIP` / `ZSTD`;
- **Партиционирование** — по какой колонке (или «нет»);
- **Обоснование** — почему выбрал именно такой формат + сжатие + партиционирование для этого слоя и твоего объёма данных.

## 6. Часть 2 — осмысление и работа с инструментами

### 6.1. Понять и объяснить

| Вопрос | Твой ответ  |
|---|---|
| Зачем нужны большие данные и lakehouse (а не обычная БД/хранилище)? | Lakehouse отделяет хранение от вычислений: большие объёмы лежат в S3, а разные движки читают одни файлы. Iceberg добавляет схему и снапшоты. Для небольших задач обычная БД проще. |
| Пример schema evolution на Silver: добавил/переименовал колонку — что произошло? | В silver.customers добавлена source_system VARCHAR, затем переименована в source_label. У существующих 150 000 строк значение NULL. Файлы не менялись, изменилась только схема. После проверки потом удалена. |
| Пример скрипта восстановления данных из снапшота (time travel) | [recovery.sql](results/recovery.sql): чтение через `FOR VERSION AS OF 7780297070286732377`, затем `ALTER TABLE lakehouse.gold.recovery_demo EXECUTE rollback_to_snapshot(7780297070286732377)`. После удаления одной строки из копии витрины восстановлены все 20 строк. |

## 7. Выводы

Bronze сохраняет исходные строки, Silver очищает и обогащает их, а Gold содержит готовый топ-20 клиентов. Parquet + ZSTD уменьшил размер Bronze на 65,6% относительно варианта без сжатия и в этом прогоне оказался выгоднее GZIP по размеру и времени записи. Партиционирование не понадобилось на таких небольших объёмах, особенно для небольших Silver и Gold. Iceberg позволил изменить схему без перезаписи файлов и восстановить данные из снапшота, а Spark подтвердил доступность тех же таблиц из другого движка.
